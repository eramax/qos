# dm-verity Key Custody

**Status:** Design only. **No verity / signing code is committed.**
The review (§2.12 and §0) is explicit: "verified boot only buys safety
if signing is real. dm-verity with ad-hoc keys in the repo is theater."
This doc is the gate: implementation does not proceed until these
questions are answered.

---

## 1. Open questions (must be answered first)

1. **Who owns the root signing key?**
   One named human, one named backup human.
2. **Where does the key live?**
   Options: YubiKey/HSM (good), encrypted file on offline laptop (ok),
   anything in CI secrets or on a build server (no).
3. **What does compromise look like, and how do we recover?**
   The dm-verity root hash is baked into the kernel cmdline. Rotating
   it means publishing a new signed kernel + a new initramfs + a new
   bootloader entry. Decide ahead of time whether we rev across
   *every* installed image (OTA-driven) or only new installs.
4. **Are images signed per-channel?**
   `stable` / `beta` / `dev` channels each get their own key? Or one
   root with subordinate signing keys per channel?
5. **What about reproducibility?**
   Signed images aren't reproducible if the signature blob is part of
   the image. Sign a *detached* artifact (PKCS#7 or minisign) stored
   alongside the image, not inside it.

## 2. Threat model (one paragraph)

We are defending against an attacker who can write to the root
partition while the system is offline (e.g. a stolen laptop, a leaked
SD card image, a malicious OTA mirror). We are *not* defending against
an attacker with code execution as root on a booted system — that is
out of scope for verity. We are also not defending against firmware
implants; Secure Boot is the layer for that and lives in
`KERNEL-SPLIT-PLAN.md` once we get there.

## 3. Layout decision (proposed)

- Each immutable root slot (`root-a`, `root-b`) gets a sibling
  `verity-a`, `verity-b` partition containing the Merkle tree.
- The Limine entry for slot N passes
  `roothash=<hex> systemd.verity=yes` on the kernel cmdline.
- The kernel cmdline itself is part of `boot/limine.conf`, which lives
  on the EFI partition. **The EFI partition is unverified**, so we
  need Secure Boot to chain trust to it. Until Secure Boot is wired,
  verity is a strong tamper-evidence mechanism but not tamper-proof.
- `qos verify` (already a placeholder in the CLI router) will mount
  the inactive slot and run `veritysetup verify` against its sibling
  hash partition. Useful before OTA activation.

## 4. Sequencing (after questions in §1 are answered)

1. Generate test keys, document the procedure in
   `scripts/dev-keys/README` (these are not the production keys).
2. Add `scripts/qos-verity-stage.sh` that, given a built rootfs image,
   computes the Merkle tree and emits `verity-a.img` + `roothash.txt`.
3. Add a Limine cmdline template variable for `roothash` and wire
   `install-limine.sh` to substitute the per-slot value.
4. Implement `qos verify` properly.
5. Add `scripts/qos-sign.sh` for the detached signature artifact.
   Calls out to whatever offline-key tool we end up using.
6. CI: build with test keys, verify, refuse to publish with test keys.
7. Cut a release using production keys, end-to-end.

Step 7 is the first time production keys touch any QOS code.

## 5. Hard "do not" list

- Do not commit any private key, even a dev key, into git. Test keys
  live outside the repo, generated by `scripts/dev-keys/` on demand.
- Do not put production keys in CI. Sign artifacts after the build,
  offline, before publishing.
- Do not call this "Secure Boot." Secure Boot is firmware-level;
  verity is dm-mapper-level. Conflating them in user-facing docs is
  the most common way these features ship broken.
